## 추가한 흐름

1. 관리자 화면에서 원본 회원·상품·검수와 소유 사업자·현재 검수 담당자 목록 조회.
2. 매핑 JSON에 상품별 소유 사업자·분류, 회원 로그인/기존 계정 연결, 실제 검수 담당자, 비표준 손상 위치 지정.
3. 원본·사진·상태·FK·계정 충돌 사전 점검. 오류가 있으면 실행 차단.
4. 회원·상품·계약·상태·사진·관찰·검수를 새 ID로 연결. 기존 비밀번호 해시·계정 상태 보존.
5. 기존 회원이 새 로그인 ID로 로그인해 본인 이력·원본 사진·손상·검수 조회.

## 기술적 처리

- V12: 실행 기록·원본→대상 ID 대응표·이전 직렬화 잠금 추가. 기존 마이그레이션과 원본 행은 수정하지 않음.
- 사전 점검 토큰에 원본·대상·매핑·사진 해시 포함. 점검 후 변경을 감지하면 재점검 요구.
- 전체 복사·대응표·실행 기록을 한 트랜잭션으로 처리. 실패 시 전부 롤백, 같은 요청 재시도는 기존 실행 결과 반환.
- 기존 현재 계정과 명시 연결 시 현재 계정의 로그인·비밀번호·역할·상태 보존. 원본에 비밀번호가 없으면 NULL 유지.
- 거절·승인·인수 등 기존 세부 단계와 원본 관찰값을 legacySource로 제공. 보류 검수는 진행 중 상태 유지.
- 과거 검수 담당자는 대응표로 직접 지정. 없는 판정 사유·사진 증거·이미지 분석 결과는 만들지 않음.

## 검증

- 실제 MySQL 8.4: 통합 테스트 40개 통과. 기존 이력 이전 19개, 기존 업무·인증·동시성·스키마 검증 21개.
- Java 실행 JAR·TypeScript/Vite 빌드 성공.
- Chrome: 관리자 매핑 누락→보완→사전 점검→이전→동일 요청 재시도 확인.
- 기존 회원 비밀번호 로그인→본인 계약·인수/반납 사진·기존/신규 손상·최종 검수 조회 확인.
- 1440×1000 / 390×844 화면, 브라우저 오류·가로 넘침 없음.
- 브라우저·DB 자료는 검증용 fixture. 사용자에게 실제 자료를 요청했으며 ‘자료 없음’ 답변을 받음. 실제 운영 이력에 적용하지 않음.

## 실제 적용에 필요한 자료

- 기존 DB 백업 또는 접근 정보.
- 기존 사진 파일과 저장 루트.
- 상품별 실제 사업자등록번호·사업자명·소유 관계 및 새 상품 분류.
- 기존 검수별 실제 담당자.
- 충돌 계정의 본인 연결 결정, 비표준 손상 위치 대응표.

실행 절차·API·상태 대응표는 RentalTrack의 [이전 안내](https://github.com/WJLee0417/RentalTrack/blob/bd98e63becf3182e4dbe3b30ea456e90877cbdbf/docs/MIGRATION.md)에 기록.
