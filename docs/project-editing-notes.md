## 1. 승객 수요 기반 차량 경로 최적화

### 현재 작업에서 살릴 중심 서사

**승객 탑승 지점·차량 배정·방문 순서의 공동 결정 문제를 모델링하고, 운행 제약을 검사하는 경로 탐색 구현.**

- 입력: 승객 수요·출발/도착 위치·거리·시간 데이터
- 제약: 허용 도보거리·차량 용량·승하차 순서·도착 시간창
- 기준 모형: 차량 이동 비용·승객 도보 비용을 반영한 Xpress Mosel
- 탐색: Python 승객 제거·재삽입과 2-opt 방문 순서 조정
- 결과: 소규모 2문제의 목적함수 값 일치, 대규모 2문제의 도착 시간창 충족

| 순서 | 작업 ID | 구체화할 설명 | 답변·자료를 받으면 반영할 내용 |
| --- | --- | --- | --- |
| 1 | FC007·FC008 | 입력에서 운행 제약까지 | 실제 입력 단위, 탑승 후보지 구성, 시간·거리 계산 기준 |
| 2 | FC009 | 비교 기준이 된 수리모형 | 결정변수, 목적함수 항과 단위, 비용 가중치, 대표 제약식 |
| 3 | FC010 | 승객 제거·재삽입 탐색 | 초기해, 제거 대상 선택, 삽입 위치 선택, 해 수용·종료 조건 |

### 먼저 받을 내용

1. 남아 있는 Mosel 파일·보고서·발표자료의 위치. Python 원본이 없다는 기존 설명은 다시 묻지 않고 유지.
2. 실제 제거·삽입 방식과 2-opt 이후 제약 검사 방법. 기억나는 동작이나 작은 사례부터 정리.
3. 왜 이 모형·탐색을 선택했는지 당시 판단. 자료에서 선택 이유가 설명된다면 해당 부분을 우선 사용.

### 편집 방향

- ‘ALNS 사용’에서 실제 경로 변경 동작과 검사 항목으로 확장.
- ‘소규모/대규모’는 규모 정의를 받은 뒤 구체화.
- 현재 흐름 도식의 세부 순서·반복 구조는 실제 구현 설명을 받은 뒤 수정.
- 실행 시간·개선율·최적성은 새로 만들지 않으며 현재 결과의 비교 대상을 유지.

## 2. RentalTrack

### 현재 작업에서 살릴 중심 서사

**반복 대여되는 상품의 상태를 계약별로 나누고, 같은 계약의 인수·반납 기록을 비교하도록 업무 흐름과 데이터 관계 설계.**

- 업무: 신청 → 인수 → 이용 → 반납 → 검수
- 모델: 상품과 개별 계약 분리
- 이력: 계약별 상태·사진·손상·검수 연결
- 협업: 필수성·구현 가능성·검증 가능성 기준 제안, 범위 조정과 명세 반영

### 편집 단위

| 순서 | 작업 ID | 구체화할 설명 | 답변·자료를 받으면 반영할 내용 |
| --- | --- | --- | --- |
| 1 | FC020 | 단계별 업무와 기록 | 누가 어느 시점에 어떤 상태·사진·검수 내용을 입력하는지 |
| 2 | FC021 | 상품과 계약을 분리한 이유 | 실제로 다룬 반복 대여 사례와 당시 엔터티·관계 |
| 3 | FC022·FC023 | 인수·반납 비교 구조 | 비교 기준, 사진·손상 연결, 검수 기록 수정·누락 처리 정책 |
| 4 | FC024 | 핵심 기능 우선순위 조정 | 실제로 논의한 기능, 먼저 하기로 정한 기능, 뒤로 미룬 기능 |

### 먼저 받을 내용

1. 당시 직접 작성한 설계·문서와 실제 구현한 기능의 구분.
2. ERD·서비스 흐름도·요구사항·API 명세 중 남아 있는 자료의 위치. 코드가 없는 설계 작업이라면 문서부터 활용.
3. 기능 우선순위를 실제로 조정한 사례 하나. 논의한 기능 → 판단 기준 → 합의한 범위 → 바뀐 문서 순서로 정리.

### 편집 방향

- 도식에 있는 엔터티 목록을 반복하는 대신 각 관계가 해결하는 업무 상황을 설명.
- 현재 포트폴리오용 개념 설계와 당시 수행한 협업 작업을 설명에 맞게 연결.
- 실제 구현이 있었다면 자료와 담당 내용을 확인한 뒤 해당 구현을 중심으로 본문 확장.
- 계약 A/B/C는 현재 가정한 예시로 유지. 실제 기록을 받으면 별도 사례로 정리.
